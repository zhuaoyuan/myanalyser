## 一、问题确认与验证结果

### 1.1 设计文档中问题描述是否属实

| 问题点 | 设计文档描述 | 代码验证结果 | 结论 |
|--------|--------------|--------------|------|
| **Filter 存在 look-ahead** | 规则 4、5 仅有 `--start-date`，会包含 T 之后数据 | 已确认：`filter_funds_for_next_step.py` 中 `_compare_detail_issue_reasons` 与 `_integrity_issue_reasons` 均仅做 `>= start_date`，无上限 | **属实** |
| **Integrity 一次只产出一个区间** | `--start-date` / `--end-date` 固定 | 已确认：`check_trade_day_data_integrity.py` 接受 start/end，产出 `details_{start}_{end}` | **属实**，但可通过拉大区间一次产出 |
| **静态参数导致不公平** | 成立年限、数据完整性若固定 2021 年后，2024/2025 回测样本集不同 | 逻辑成立：若 filter 用 `2021-01-01`，不同 T 的 lookback 实际窗口不同 | **属实** |
| **Prep 支持按 T 调用** | `--date` 控制 eligible 集合 | 已确认：`_apply_filters(date_str)` 按 date 筛选成立日、规模、机构持仓等 | **属实** |
| **Scoreboard 支持截断** | `--latest-nav-date` | 已确认：`pipeline_scoreboard.py` 在净值/人事计算中均做 `<= latest_nav_date` | **属实** |

### 1.2 行业实践对照

- **Look-ahead bias**：量化回测中若使用未来信息，会导致回测表现虚高、实盘失效，已被广泛识别（参考 Enjine、Algotradinglib 等）。
- **Point-in-Time 数据**：金融建模中标准做法是按决策时点 T 截断，仅使用 T 及之前可观测数据；与设计文档中的「宽存窄用」完全一致。
- **公平可比性**：同一策略在不同时点回测时，应保持相同相对条件（如 lookback 3 年、持有期 42 日），否则无法做跨年对比。

## 二、方案评估

### 2.1 核心原则：宽存窄用

| 维度 | 评估 | 说明 |
|------|------|------|
| **合理性** | ✅ 强烈推荐 | 与金融回测行业实践一致，消除 look-ahead、保证公平性 |
| **实现成本** | 中 | 主要在 filter 增加 `--end-date`，其余模块已有或可轻量扩展 |
| **数据成本** | 低 | 原始 ETL 本就全量，Integrity 拉大区间仅增加一次计算 |

### 2.2 Filter 增加 `--end-date`（P0）

| 维度 | 评估 | 说明 |
|------|------|------|
| **必要性** | ✅ 必须 | 当前无上界，明确存在 look-ahead |
| **改动范围** | 小 | `filter_funds_for_next_step.py`：规则 4 用 `期初日期 <= end_date`，规则 5 用 `交易日日期 <= end_date` |
| **向后兼容** | 易 | `--end-date` 可选，不传时沿用「无上界」或默认 `INTEGRITY_END_DATE` |
| **风险** | 低 | 纯逻辑改动，不影响 ETL/Compare 产出格式 |

### 2.3 Integrity 最大跨度（P0）

| 维度 | 评估 | 说明 |
|------|------|------|
| **必要性** | ✅ 推荐 | 一次产出全跨度，供多 T 复用，符合宽存 |
| **改动范围** | 极小 | 仅环境变量默认值调整（如 `INTEGRITY_START_DATE=2012-01-01`） |
| **兼容性** | 好 | 已有 run 可继续用原区间；新 run 或重跑 step4 时采用新默认 |
| **注意** | 一次计算量略增 | 区间变长，但 integrity 本身为全基金扫描，可接受 |

### 2.4 Prep 按 T 调用：形态 A vs 形态 B

| 形态 | 描述 | 优点 | 缺点 | 建议 |
|------|------|------|------|------|
| **A：prep_eligible_from_cached** | 新模块，只读已有 CSV 做筛选 | 与 prep 主流程解耦，无网络；适合回测编排 | 需维护两套入口 | **推荐**，用于回测编排 |
| **B：prep --date T --skip-fetch** | 扩展现有 CLI | 单入口 | `--skip-fetch` 语义复杂，易与主流程耦合 | 可作为补充，非首选 |

### 2.5 L3 参数化缓存

| 维度 | 评估 | 说明 |
|------|------|------|
| **价值** | 高 | 多 T 滚动回测时，filter/prep/scoreboard 按 (T, lookback) 重复计算，缓存收益大 |
| **优先级** | P2 | 可在 P0/P1 落地后再建，避免首轮实现过重 |
| **缓存键设计** | 合理 | `(run_id, filter_start, filter_end)` / `(run_id, latest_nav_date)` 等，设计文档已覆盖 |
| **失效策略** | 可行 | run_id 变更即整 run 失效，简单清晰 |

### 2.6 回测编排层（单 T vs 多 T 滚动）

| 模式 | 评估 | 说明 |
|------|------|------|
| **单 T** | 高优先级 | 与现有 verify、生产榜单一致，先支持 |
| **多 T 滚动** | P2 | 用于多年公平对比，依赖 L3 缓存与 prep_eligible_from_cached |

## 三、风险与缓解

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| Filter 增加 `--end-date` 后，现有单次跑结果变化 | 中 | 预期变化：结果更保守（剔除 look-ahead）。需在需求日志中说明，并在验收中对比改动前后 |
| Integrity 最大跨度导致 step4 耗时增加 | 低 | 区间拉长，但一次计算；若过慢可考虑按年分批后再合并（非首版必需） |
| prep_eligible_from_cached 与 prep 主流程逻辑分叉 | 中 | 抽取共享筛选函数到 `_apply_filters` 核心逻辑，两入口共用 |
| L3 缓存目录膨胀 | 低 | 按 run_id 隔离，定期清理或设置 TTL |

## 四、建议总结

### 4.1 优先实施（P0）

1. **Filter 增加 `--end-date`**  
   - 修改 `filter_funds_for_next_step.py`：规则 4、5 增加上界判定。  
   - 修改 `run_full_pipeline.sh`、`verify.sh`：传入 `--end-date`，默认 `INTEGRITY_END_DATE` 或 AS_OF_DATE。  
   - 消除 look-ahead，是本次改进的核心。

2. **Integrity 默认最大跨度**  
   - 调整默认：`INTEGRITY_START_DATE=2012-01-01`，`INTEGRITY_END_DATE` 保持当天或数据末端。  
   - 新 run 或重跑 step4 时采用新区间。

### 4.2 次优先（P1）

3. **实现 prep_eligible_from_cached**  
   - 新增 `src/transforms/prep_eligible_from_cached.py`，从 work_dir 读 CSV，仅执行 `_apply_filters(date)`。  
   - 供回测编排按 T 产出 eligible 集合，无需网络。

4. **单 T 回测编排支持 (filter_start, filter_end)**  
   - 回测时对每个 T 传入 `filter_start=T-lookback`、`filter_end=T`。  
   - 与 verify 行为对齐，并支持未来多 T 扩展。

### 4.3 可延后（P2）

5. **L3 缓存**：filter、scoreboard 按参数缓存。  
6. **多 T 滚动回测编排器**：T 列表 + 汇总对比。  
7. **Prep eligible 缓存**：与 L3 集成。

### 4.4 验收要点

- Filter 改动后，需增加/更新单测：验证 `--end-date` 正确截断规则 4、5。  
- 回归测试：`make verify` 或 `bash tools/verify.sh` 全绿。  
- 可选：用同一 run_id，对比增加 `--end-date` 前后的 filter 结果数量与名单变化，文档化预期差异。

---

## 五、结论

设计文档中的问题分析**准确**，方案**合理且可落地**。「宽存窄用」与量化回测中的 Point-in-Time 实践一致，能有效消除 look-ahead、保证跨时点公平可比。

建议按文档中的阶段划分执行：**Phase 1 以 Filter 增加 `--end-date` 为核心**，配套 Integrity 最大跨度与 pipeline 传参，即可显著改善当前公平性问题；后续再逐步推进 L3 缓存与多 T 编排。
