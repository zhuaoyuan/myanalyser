# 宽存窄用与回测公平性设计

日期：2026-03-15

## 1. 背景与目标

> 讨论一个设计问题。当前使用@myanalyser/tools/prep/prep_data_workflow.py -> @myanalyser/tools/run_full_pipeline.sh 。这个工作流来准备基金回测数据。对于基金成立年限、数据完整性比对时长等时间方面的维度，目前处理是静态的（在参数中规定）。这是有问题的。因为这会使得：假设参数中规定成立年限和数据完整性都卡在2021年1月之后，那么2024年回测样本集为成立3年以上的基金，2025年回测样本集为成立4年以上的基金，这是不公平的。

希望「一步到位」地增强数据兼容性，使最终准备好的数据能够支持：

- 从**任意不同时间点**（如 2015 年、2025 年）采集**同等历史时间窗口**数据（如各自时间点前的 3 年）作为条件
- 用**同等未来时间窗口**（如各自时间点后的 42 个交易日）表现验证
- 对各时间点的回测结果保持**公平可比**

## 2. 核心原则：宽存窄用

> **数据准备阶段尽可能多地保留原始数据；截取、加工、校验、筛选、使用推迟到回测阶段，按每个模拟时点 T 按需进行。**

```
数据准备阶段                    回测阶段（每个 T）
─────────────────────────────────────────────────────────────
尽可能多保留原始数据     →     按 T 截取、加工、校验、筛选、使用
（宽存）                        （窄用）
```

| 阶段 | 职责 | 示例 |
|------|------|------|
| **数据准备** | 采集并保留全跨度原始数据，不做或少做按日期裁剪 | ETL 全历史 NAV/分红/拆分/规模/持有人；integrity、compare 产出覆盖全跨度的明细 |
| **回测** | 对每个模拟日 T，按需截取、加工、校验、筛选、使用 | filter 只用 [T-lookback, T] 区间；scoreboard 用 `--latest-nav-date=T`；eligible 集用 prep `--date T` 产出 |

## 3. 公平性要求

| 维度 | 2015-06-01 模拟 | 2025-06-01 模拟 | 公平性含义 |
|------|-----------------|-----------------|------------|
| 条件窗口 | [2012-06-01, 2015-06-01] | [2022-06-01, 2025-06-01] | 相同相对窗口（各为 T 前 3 年） |
| 验证窗口 | [2015-06-01, T+42 交易日] | [2025-06-01, T+42 交易日] | 相同未来长度（42 交易日） |
| 无前瞻 | T 时点只用 T 及之前数据 | 同上 | 严格点时间约束 |

## 4. 当前设计与待改进点

| 环节 | 现状 | 问题 |
|------|------|------|
| **Integrity** | `--start-date` / `--end-date` 固定 | 一次只产出一个 [start,end] 的报告；应使用最大跨度一次产出，供多 T 复用 |
| **Compare** | 按基金处理全量数据，明细含期初/期末日期 | 支持任意区间切片，无需改动 |
| **Filter** | 仅有 `--start-date`（指定日期后），无 `--end-date` | **存在 look-ahead**：会包含 T 之后的数据，需增加 `--end-date` |
| **Prep** | `--date` 控制「截至某日」的 eligible 集合 | 设计已支持点时间，可对每个 T 调用 |
| **Scoreboard** | 支持 `--latest-nav-date` | 已支持，可按 T 截断 |

## 5. 推荐方案：最大跨度 + 时点参数化

### 5.1 数据准备（一次性）

```
INTEGRITY_START_DATE = 2012-01-01
INTEGRITY_END_DATE   = 2026-12-31
FILTER_START_DATE    = 2012-01-01  # pipeline 默认值，回测时会被覆盖
```

一次产出 integrity、compare 全跨度明细；原始数据不做裁剪。

### 5.2 Filter 必须支持 `--end-date`

规则 4、5 仅在 `[start_date, end_date]` 内判定，回测时对每个 T 传入：

- `filter_start = T - lookback`
- `filter_end = T`

### 5.3 回测时按 T 参数化

| 步骤 | 参数 | 含义 |
|------|------|------|
| Prep eligible | `--date T` | T 时点的 eligible 基金集合 |
| Filter | `--start-date T-3y` `--end-date T` | 仅判定 [T-3y, T] 内的数据质量 |
| Scoreboard | `--latest-nav-date T` | 只用 T 及之前的净值 |
| Backtest | `start=T`, `end=T+42交易日` | 持有期验证 |

## 6. 缓存模块设计

多次回测需要共享中间数据，需较充分的缓存能力。

### 6.1 缓存层次

| 层级 | 内容 | 计算成本 | 复用方式 | 当前状态 |
|------|------|----------|----------|----------|
| **L1 原始数据** | ETL 产出（NAV、分红、拆分、overview、cyrjg、gmbd、fee） | 高 | 按 `run_id` 持久化 | ✅ 已有 |
| **L2 全跨度明细** | integrity 明细、compare 明细 | 中 | 一次产出，多回测复用 | ✅ 已有 |
| **L3 参数化中间** | filter 结果、prep eligible、scoreboard | 中~高 | 按 `(T, lookback)` 等参数缓存 | ❌ 待建 |
| **L4 回测结果** | period_detail、report | 低 | 按配置缓存 | 可选 |

### 6.2 L3 参数化缓存键

| 对象 | 缓存键 | 依赖 |
|------|--------|------|
| Filter 结果 | `(run_id, filter_start, filter_end)` | L1 + L2 |
| Prep 合格集 | `(prep_inputs_hash, date)` | L1 |
| Scoreboard | `(run_id, latest_nav_date)` | L1 |

### 6.3 失效策略

- **run_id 变更**：该 run 下 L2、L3 缓存失效
- **Prep 输入变更**：按 mtime 或 hash 失效对应 prep 缓存
- **参数变更**：对应 filter/scoreboard 缓存失效

### 6.4 目录示意

```
cache_root/
  filter/
    {run_id}/
      {filter_start}_{filter_end}/
        filtered_fund_candidates.csv
  prep/
    {inputs_id}/
      {date}/
        prep_result.csv
  scoreboard/
    {run_id}/
      {latest_nav_date}/
        fund_scoreboard_*.csv
```

## 7. 回测编排层（Backtest Runner）重设计

### 7.1 单 T 回测 vs 多 T 滚动回测

| 模式 | 输入 | 输出 | 用途 |
|------|------|------|------|
| **单 T** | 单个 `as_of_date=T` | 一次回测报告 | 生产榜单、验证、手动回测 |
| **多 T 滚动** | T 列表或 `[T_start, T_end, step]` | 多份报告 + 汇总 | 多年公平对比、策略稳定性评估 |

### 7.2 单 T 回测流程（与现有 verify 对齐）

```
输入: run_id, as_of_date=T, lookback=3年, hold_days=42

1. prep_eligible(T)     ← 从 L1 加载 cyrjg/gmbd/overview/fee，仅做 _apply_filters(date=T)，可选 L3
2. filter(T-3y, T)     ← 规则 4、5 仅判 [T-3y, T]，可选 L3
3. 交集: eligible ∩ (purchase - filtered_out)
4. scoreboard(T)       ← --latest-nav-date T，可选 L3
5. backtest(start=T, end=T+42交易日)
```

### 7.3 多 T 滚动回测流程

```
输入: run_id, T_list=[2015-06-01, 2016-06-01, ..., 2025-06-01], lookback, hold_days

for T in T_list:
    result[T] = 单_T_回测(run_id, T, lookback, hold_days)  # 内部命中 L3 则跳过计算

汇总: 各 T 收益曲线、夏普、回撤等，支持年度横向对比
```

### 7.4 Prep 按 T 调用的实现形态

Prep 的 cyrjg、gmbd、overview、fee 等**不依赖 T**，仅 `_apply_filters` 依赖 T。因此：

- **形态 A（轻量）**：拆出 `prep_eligible_from_cached(date, work_dir)`，从 work_dir 读已有 CSV，只执行筛选逻辑，不触发网络
- **形态 B（CLI 兼容）**：`prep_data_workflow.py --date T` 支持 `--skip-fetch`（当 work_dir 已有 a/b/c/e 时跳过抓取），直接走 _apply_filters

推荐形态 A：新增 `src/transforms/prep_eligible_from_cached.py`，供回测编排调用，与 prep 主流程解耦。

## 8. 兼容性策略

### 8.1 向后兼容：当前单次跑

| 场景 | 行为 | 实现 |
|------|------|------|
| run_full_pipeline 单次跑 | 等价于单 T，T = 数据最新净值日 | 隐式 `as_of_date=AS_OF_DATE`，filter 用 `--end-date AS_OF_DATE` |
| verify.sh | 同上，T 固定为验证用区间 | 保持不变，仅 filter 增加 end-date 传参 |

### 8.2 环境变量兼容

| 变量 | 宽存窄用语义 | 兼容策略 |
|------|--------------|----------|
| `INTEGRITY_START_DATE` | 全跨度左边界 | 调大默认值（如 2012-01-01），旧 run 若已产出可继续用原区间 |
| `INTEGRITY_END_DATE` | 全跨度右边界 | 默认当天或数据末端 |
| `FILTER_START_DATE` | 单 T 模式下的 filter 左边界 | 保持，单 T 时 filter_end=AS_OF_DATE |
| `FILTER_END_DATE` | **新增** | 单 T 模式默认=AS_OF_DATE；多 T 模式由编排传入 |

### 8.3 渐进迁移

1. **Phase 1**：Filter 增加 `--end-date`，pipeline 传 `end_date=INTEGRITY_END_DATE`，消除 look-ahead
2. **Phase 2**：Integrity 拉至最大跨度（新 run 或重跑 step4）
3. **Phase 3**：实现 `prep_eligible_from_cached` + L3 缓存框架
4. **Phase 4**：实现多 T 滚动回测编排器

## 9. 缓存实现细化

### 9.1 Prep 缓存键的实用化

`prep_inputs_hash` 可用以下代替，避免对大盘 CSV 做全文 hash：

- `(purchase_mtime, cyrjg_mtime, gmbd_mtime, fee_mtime, overview_mtime)` 的元组
- 或简化为 `run_id`（当 prep 输入与 run 绑定时）

若 prep 输入来自 `data/common/cached_prep/` 等固定目录，可直接用目录路径 + 最后修改时间。

### 9.2 Filter / Scoreboard 缓存命中

- Filter：纯 CPU，开销小，缓存主要减少 I/O 与重复逻辑
- Scoreboard：计算重，缓存收益高，优先保证 `(run_id, latest_nav_date)` 命中

### 9.3 缓存目录与 run_id 的关系

建议 L3 与 `artifacts/full_run_{run_id}` 或 `data/versions/{run_id}` 对齐：

```
data/versions/{run_id}/
  fund_etl/                    # L1
  cache/                       # L3（可选独立目录）
    filter_{start}_{end}/
    prep_eligible_{date}/
    scoreboard_{latest_nav_date}/
```

便于 run_id 变更时整目录清理失效。
